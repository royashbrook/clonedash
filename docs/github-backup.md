# Private backup pilot

More → Account is optional. Signing in enables automatic backup of progress, settings and saved levels, skins, loops and songs. Uncommitted editor changes are not part of a save. Guest play and file export still work offline. No leaderboard, uploads to the catalog or content license is involved.

Players do not register an app or create a repository. Start in **Account → Sign in with GitHub**. If the app isn't installed, the game sends the player to GitHub for consent and resumes sign-in on return. The first login reserves a unique name and requests one initialized private personal repository from `POST /user/repos` with the player's GitHub App token. The next login uses the saved numeric repo ID. A pre-created repo is not a substitute for this flow.

Use [repository creation (write)](https://github.blog/changelog/2026-10-13-github-app-improvements-for-least-privilege-and-management/) and contents read/write, not administration or a classic OAuth repo scope. The server refuses blanket grants and selections containing unrelated repositories. If GitHub's consent UI cannot grant the app access starting from zero selected repos, that blocks this design. Do not ask a player to select an unrelated repo to get past it.

The server checks the one pilot user on login and the one installation, repository ID, owner and visibility on file operations. It writes only `cube-dash.cdb` on the default branch. Git keeps the previous commits. This is not encryption against the repository owner, its collaborators, or a subsequent visibility change. Do not make the repo public. The player may export their save without GitHub at any time.

The client checks for changes every 30 seconds while connected, and at visibility changes. An app force-quit or offline device may not have uploaded its last change. Acknowledgement from GitHub is required to say it is backed up. The next session checks again. If the remote does not match the revision known to the device, pause for review. Restore replaces the device; it does not merge two games. Export local work first if needed. Signing out stops cloud saves and keeps both copies.

## Operator checklist

1. Register one GitHub App for the game. Use the game origin plus `/api/backup/callback` for OAuth and `/api/backup/installed` for the installation setup URL. Leave OAuth during installation off so the setup URL receives the installation return. Enable expiring user tokens; leave webhooks, device flow, account email, administration and organization permissions off. Keep the pilot private and allowlisted. Do not install it against an existing repo for the test. Use secure input for the client secret; no credentials or callback queries in logs or issues.
2. Bind a dedicated D1 database as `SESSIONS`, initialized with [the schema](../backup/session.sql). Store `PILOT_CLIENT_SECRET` as a Worker secret; configure `PILOT_CLIENT_ID`, `PILOT_USER_ID`, `PILOT_APP_SLUG`, and the exact HTTPS `PILOT_ORIGIN`. There is no operator-supplied repo ID. Missing bindings or a different host disable the API. The DB holds the per-account repo binding, session hashes and private OAuth credentials, never game saves. Restrict access including backups; sign-out deletes the session, and sessions expire after 30 days. Set a retention policy for expired credentials and DB backups before widening the pilot.
3. Before calling it live, check the deployed Worker with its real D1 binding, the OAuth return in an installed iOS PWA, correct private destination, two distinct browser sessions, conflict, logout and revocation. The browser tests use a simulated service; they do not establish that the GitHub or iOS authorization flow works. Leave the pilot off until the real integration and review are complete.
